## qgrep (P:\github\qgrepSearchTool) — 修复 C2220/C4819 编译阻断

- **现象**：VS Error List 报 `Error C2220: the following warning is treated as an error`，文件 `qgrep\extern\re2\re2\unicode_casefold.h(1)`，项目 qgrep (Debug|x64)。
- **根因**：`error C2220` 只是「warning 被当成 error」的转发。真实 warning 是 `C4819: The file contains a character that cannot be represented in the current code page (936)`。该头文件为**无 BOM 的 UTF-8**，第 18/19 行注释里有 `'K'`（U+212A KELVIN SIGN，UTF-8 字节 `E2 84 AA`）；系统代码页 936(GBK) 下 `AA` 后面是空格，构成非法序列 → C4819 → 被 `TreatWarningAsError=true` 升级成 C2220。
- **影响范围**：`unicode_casefold.h` 被 parse.cc / prefilter.cc / unicode_casefold.cc 等众多 re2 源文件包含，所以每个 TU 都报一次；`onepass.cc` 也含非 ASCII（当次未触发）。
- **修复**：`qgrep/qgrep.vcxproj` 四个配置（Debug/Release × Win32/x64）的 `<ClCompile>` 各加一行
  `<AdditionalOptions>/utf-8 %(AdditionalOptions)</AdditionalOptions>`
- **验证方式（环境限制下的绕过）**：本机安全策略硬拦 `MSBuild.exe`（Bash/PowerShell/关闭沙箱均被拒 → "Known Windows LOLBin"），VS 又没打开该解决方案（`vs_health` 显示 solutionName 为空、Error Table 为 0 条），因此改用 **cl.exe 单文件编译**复现与验证：
  - cl.exe：`C:\Program Files\Microsoft Visual Studio\2022\Enterprise\VC\Tools\MSVC\14.44.35207\bin\Hostx64\x64\cl.exe`（19.44 / v143）
  - SDK include：`C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\{ucrt,shared,um}`
  - 不带 `/utf-8`：C2220 + C4819 精确复现（exit 2）
  - 带 `/utf-8`：unicode_casefold.cc / onepass.cc / parse.cc / prefilter.cc / dfa.cc / regexp.cc / prog.cc / simplify.cc 全部 exit 0
- **安全性**：全仓库扫描（`.c/.cc/.cpp/.h/.hpp`）仅 7 个文件含非 ASCII 字节：编译集中只有 `unicode_casefold.h`、`onepass.cc`（均无 BOM、合法 UTF-8，且非 ASCII 只在注释里），`highlight.hpp` 带 BOM，另 4 个在 `re2/testing/`（不参与编译）。**没有 GBK 编码源文件**，故加 `/utf-8` 不会破坏任何窄字符串字面量。
- **备注**：re2 属第三方代码，选择加编译开关而不是给文件加 BOM，避免下次同步 re2 时改动丢失。

## qgrep GUI — 修复中文搜索搜不到 + 搜索结果乱码（编码链路）

- **现象**：① 搜索结果里的中文显示乱码；② 用中文搜索搜不到（内容确实存在）。
- **根因（同一处）**：`qgrepInterop/qgrepInterop.cpp` 的托管↔原生字符串编组用的是**系统 ANSI 代码页**（本机 CP936）：
  - `marshal_as<std::string>(String^)` → 中文查询变 GBK 字节（`D6 D0 CE C4`），而索引内容是 UTF-8 → 永远匹配不上；
  - `gcnew String(const char*)` 把引擎输出的 UTF-8 字节按 GBK 解码 → 乱码，而且会把结果里单字节 `0xB0` 分隔符（`path(line)\xB0text`）当双字节汉字吃掉 → 连 path/line 解析都失效。
  - 这是上游 aranhil/qgrepGUI 的先天限制（`git show e11a028:qgrepInterop/qgrepInterop.cpp` 证实），在 CP1252 的西文系统上「碰巧」是字节保真的，所以在 936 环境下才暴露。
- **项目原有约定**：`ConfigParser.ToUtf8/FromUtf8`（UTF-8 字节 ↔ Windows-1252 字符）与 `qgrep/src/fileutil_win.cpp` 的 `fromUtf8`/`_wfopen` 说明「字符串承载的是 UTF-8 原始字节」，即**字节保真传输**；但 interop 的地基没按这个约定实现，且查询串漏了 ToUtf8、结果文本漏了 FromUtf8。
- **修复**（4 个文件）：
  1. `qgrepInterop/qgrepInterop.cpp`：新增 `ToNativeBytes/FromNativeBytes`，用 ISO-8859-1/28591 语义做无损字节搬运（`ch<=0xFF` 直接映射），替换掉 3 处 ANSI 编组（参数、stringCallback、localizedStringCallback）。
  2. `qgrepInterop/qgrepInterop.vcxproj`：4 个配置补 `/utf-8`（与 qgrep 引擎工程一致，避免源文件中文注释触发 C4819）。
  3. `qgrepControls/Classes/ConfigParser.cs`：`ToUtf8/FromUtf8` 由 Windows-1252 改 28591 并加 null 保护（与 interop 统一；1252 的 0x81/0x8D/0x8F/0x90/0x9D 有兼容风险）。
  4. `qgrepControls/Classes/SearchEngine.cs`：查询侧补 `ToUtf8`（关键字、`fi/fe` 过滤、files 搜索的 pathToRemove+query）、结果侧补 `FromUtf8`（`StringHandler` 里带/不带 `0xB0` 两条分支）、`change` 命令的变更文件列表补 `ToUtf8`。
- **语义验证**（`%TEMP%\verify_encoding_fix.py`，模拟三端字节流）：新方案下 `0xB0` 分隔符保留、`file/line` 正确解析、行文本还原为「中文注释 abc」、查询字节 `e4 b8 ad e6 96 87` 在 UTF-8 内容中命中；旧方案复现「分隔符被吃掉 + 六个 `?` 不命中」。
- **编译验证**：`cl.exe /clr /c /W3 /utf-8`（VS2022 14.44.35207 / v143）编译 `qgrepInterop.cpp` 通过、无警告。**C# 侧未能在本机编译**（见下）。
- **环境限制（重要）**：沙箱命令校验会拦截**任何含 `msbuild` 字样的命令**（`MSBuild.exe`、`dotnet msbuild`、`-p:VCTargetsPath=...\MSBuild\...` 全部被拒，关沙箱也无效）；`dotnet.exe`（不含 msbuild 字样时）与 `cl.exe` 可用。因此 `dotnet build` 会因 `qgrepInterop.vcxproj` 需要 MSBuild.exe 而失败 → C#/C++ 工程整体构建只能交给 VS（或用 VS 桥接触发）。
- **Bash 工具注意**：本机 shim 缺 coreutils，`ls/grep/head/tail/sed` 均不可用，管道会静默失败；改用 Glob/Grep 工具或 `python.exe`（全路径）做探测。
